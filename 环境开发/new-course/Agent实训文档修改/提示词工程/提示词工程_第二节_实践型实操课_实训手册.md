# 提示词工程 · 第二节：工程化实战工作坊 —— 构建你的万能文案生成器

> 本实训手册指导你运用五大工程化原则（模块化、参数化、可测试、版本化、可观测）构建一个可复用的提示词系统。实战案例：为智能降噪耳机构建万能文案生成器。课程时长45分钟。

## 步骤 1: 了解挑战目标与交付标准

**挑战任务：为一款"智能降噪耳机"构建万能文案生成器**

## 步骤 2: 理解模块设计原则

**阶段一：模块设计 —— 体现模块化 Modularity**

设计并编写3个核心模块，每个模块需要满足：

- **独立性**：可以单独使用，不依赖其他模块
- **复用性**：可以用于不同场景和产品
- **边界清晰**：有明确的输入输出定义

### 模块模板

```
# ===== 模块：[模块名称] =====
# 版本：v1.0
# 功能：[简述这个模块的作用]
# 作者：[小组名]
# ---------------------------
[在此编写模块内容]
```

### 可选模块清单

学员从以下模块中选择3个进行编写：

| 模块 | 功能 | 设计要点 |
|------|------|----------|
| **角色模块** | 定义AI的身份和能力 | 专业背景、擅长领域、风格特点 |
| **产品模块** | 封装产品信息 | 名称、卖点、价格、差异化 |
| **平台模块** | 定义平台规则 | 调性、格式、字数、禁忌 |
| **受众模块** | 定义目标用户 | 痛点、场景、语言偏好 |
| **风格模块** | 定义文案调性 | 活泼/专业/高级的具体表现 |
| **格式模块** | 定义输出结构 | 字数、段落、标点、emoji |

## 步骤 4: 编写平台模块（参考示例）

**示例：平台模块 - 小红书**

```
# ===== 模块：平台模块 - 小红书 =====
# 版本：v1.0
# 功能：定义小红书平台的内容规则和调性
# ---------------------------

平台特性：种草型社区，用户追求真实体验分享

内容调性：闺蜜聊天式、真诚分享、适度"真实的不完美"

格式要求：
- 标题：带emoji，有悬念或痛点共鸣，15字以内
- 正文：口语化、分段短、善用emoji做视觉分隔
- 字数：300-500字
- 结尾：软性互动引导（"姐妹们你们觉得呢？"）

禁忌：硬广感、价格直接写、过度吹捧、绝对化用语
```

## 步骤 7: 理解参数化设计原则

**阶段二：参数定义 —— 体现参数化 Parameterization**

核心思路：**固定部分（模板） + 可变部分（参数） = 最终提示词**

### 参数表设计

| 参数名 | 类型 | 必填 | 默认值 | 可选值/说明 |
|--------|------|------|--------|-------------|
| {{platform}} | 枚举 | 是 | - | 小红书/抖音/公众号/淘宝/朋友圈 |
| {{audience}} | 枚举 | 是 | - | 通勤族/远程办公者/游戏玩家 |
| {{tone}} | 枚举 | 否 | 活泼 | 活泼/专业/高级/接地气 |
| {{word_count}} | 数字 | 否 | 300 | 100-800之间 |
| {{include_price}} | 布尔 | 否 | true | 是否显示价格信息 |
| {{promotion}} | 文本 | 否 | 无 | 促销信息（如有） |

## 步骤 11: 使用评分卡量化质量

### 评分卡（Scorecard）

| 维度 | 分值 | 评判标准 |
|------|------|----------|
| **格式合规** | 20分 | 符合平台格式要求（字数、emoji、结构） |
| **卖点传达** | 25分 | 3个核心卖点至少体现2个，且表达自然 |
| **人群匹配** | 25分 | 场景、痛点、话术符合目标受众特征 |
| **吸引力** | 20分 | 开头有吸引力，整体有记忆点 |
| **文字质量** | 10分 | 通顺、无语病、无明显AI味 |

## 步骤 14: 理解迭代优化原则

**阶段四：迭代优化 —— 体现版本化 Versioning + 可观测 Observability**

### 观测分析模板

```
# 问题观测记录

## 发现的问题
| 问题编号 | 问题描述 | 出现频率 | 严重程度 |
|----------|----------|----------|----------|
| P001 | 小红书文案开头太正式，缺乏吸引力 | 2/2次 | 高 |
| P002 | 通勤场景描写不够具体 | 1/2次 | 中 |

## 根因分析
P001: 平台模块中缺少"开头钩子"的明确要求
P002: 受众模块的场景描述太笼统，缺少具体词汇

## 优化方案
1. 在小红书平台模块增加："开头必须用提问/痛点/悬念吸引注意"
2. 在通勤族受众模块增加场景词库："早高峰""换乘""人挤人"
```

## 步骤 19: 总结升华——从实践到思维转变

### 今日核心收获

| 原则 | 你学到了什么 |
|------|-------------|
| **模块化** | 拆分让系统可复用、可维护——像乐高一样自由组合 |
| **参数化** | 配置化让系统灵活适应不同场景——一套模板多种输出 |
| **版本化** | 记录让迭代有迹可循——随时回溯、对比、回滚 |
| **可测试** | 量化让质量有标准可依——用数据说话而非感觉 |
| **可观测** | 数据让优化有方向可循——精准定位问题根因 |

### 思维转变

| 从前 | 现在 |
|------|------|
| 每次写提示词都是"重新创作" | **提示词是一个"可运维的系统"** |
| 好不好全凭感觉 | **好不好看测试数据** |
| 改了就忘了 | **每次改动都有记录，随时可回溯** |
| 出问题靠猜 | **出问题看数据、找根因** |

### 延伸思考

> *如果这个文案生成器要部署到公司实际业务中，还需要考虑什么？*

- 如何处理新平台上线？——模块扩展机制
- 如何让运营同事自己配置参数？——配置界面设计
